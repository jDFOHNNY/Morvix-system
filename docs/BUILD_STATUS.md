## Device status diagnosis and manual text check

The status mismatch was caused by stale dashboard rendering, not a missing backend check-in update. `POST /api/v1/extension/activate` initializes `paired_at` and `last_seen_at`; authenticated `GET /api/v1/extension/policy` updates `last_seen_at` on each policy sync. The extension popup syncs policy when opened, and the service worker requests policy sync on its one-minute alarm. The separate authenticated `POST /api/v1/extension/heartbeat` endpoint also updates last-seen, but the extension currently uses policy sync as its recurring check-in. Dashboard status is connected only when the server reports a non-revoked device seen within 120 seconds.

Before this fix, Settings fetched devices during initial render and after creating a pairing code or revoking a device. It did not refresh after the extension consumed the code; the Overview banner also remained unchanged until a route render. The dashboard now refetches server status on a 10-second interval while Overview or Settings is active, and immediately when the dashboard window/tab becomes visible again. On a backend error, it keeps the last server result; it never infers an online state from a local timer.

The controlled page is served at `http://localhost:8001/MORVIX_plain_text_demo.html`, on a hostname separate from the dashboard/backend host `127.0.0.1`. This avoids registering the content script on the MORVIX dashboard host for this test. From PowerShell:

```powershell
.\.venv\Scripts\python.exe -m http.server 8001 --bind localhost --directory .\data\controlled_extension_test
```

Open that URL, refresh the dashboard tab once so it loads the updated dashboard code, then reload the unpacked MORVIX extension in Chrome before testing. On the test page, open the MORVIX popup and click **Enable protection on this site**; Chrome may prompt to grant access to `http://localhost/*`. The existing `matchFor` logic does not put ports into Chrome match patterns, so that permission applies to the `localhost` host across ports; keeping the test at `localhost` separates it from the dashboard/backend host `127.0.0.1`. The page's visible benign sentence, fictional test sentence, labels, and limitations are all part of the combined text sent for analysis. The updated workspace source now handles successful results, malformed responses, timeouts, and backend outages with regression coverage. The user's Chrome window was not available in the connected browser inventory during this review, so the actual classifier notice, policy action, event persistence, and refreshed dashboard still need manual verification.

The content script extracts visible rendered text (up to 20,000 characters, after its site-policy gate and only when text policy is enabled). It analyzes any nonempty initial snapshot and debounces rescans after DOM text changes; a short-lived fingerprint avoids resending an unchanged snapshot, and raw page text is not persisted by the extension. The service worker sends `POST http://127.0.0.1:8000/api/v1/extension/classify/text` with a device bearer token and JSON `{text, source_url, event_key}`; `source_url` is the page origin only and `event_key` is a UUID. The authenticated backend checks active policy, website-rule precedence, modality enablement and classifier availability, then runs the experimental local text model over overlapping token windows and evaluates configured category/review/block thresholds. A completed result for a supported category is saved as metadata-only history even when the final action is Allow below the review threshold; `record_detection` is idempotent for an `event_key` and creates alerts only for Warn/Block. Paused or preempted classification paths and unavailable/unsupported results do not create category events. Dashboard Detection History reads `GET /api/v1/events`; Alerts reads `GET /api/v1/alerts`; Overview reads `GET /api/v1/dashboard/summary`. Browser classification, event persistence, and refreshed dashboard display remain unverified until the controlled Chrome test is completed.

The marked SRS dashboard row is now reflected in the Overview source and covered by dashboard/backend regressions. The modality filter applies to recent records; the selected range applies to counts and analytics; current unreviewed alerts appear directly on Overview. Audio stays absent because no audio event modality/classifier is enabled. See `REQUIREMENTS_TRACEABILITY.md` for requirement-by-requirement status and remaining model/Chrome gaps.

## Open decisions and limitations

- The supplied SRS leaves final taxonomy, thresholds, browser target, video strategy, data-retention period, deployment topology, and performance targets for adviser/team confirmation. Provisional choices are in `DECISIONS_AND_LIMITATIONS.md`.
- The threat model output is English toxic-comment `threat`, not a validated general threat detector. There is no configured self-harm model.
- The local text snapshot is the uncased English toxic-comment model, not the model card's separate multilingual XLM-R variant. It uses overlapping 512-token windows with a 64-token overlap, capped by 20,000 characters; profanity and identity-related language can affect scores regardless of intent. The maximum window score is not calibrated. MORVIX has no held-out language, bias, calibration, or accuracy evaluation, and the model does not output violence or self-harm categories.
- A compatible image classifier with verifiable output labels and appropriate license must be selected before image scoring can be enabled. Video uses a separate candidate classifier and returns a model score, but that model has not been evaluated against MORVIX data and is not validated for the draft's “graphic violence” definition.
- Self-harm is currently a policy taxonomy entry only; there is no self-harm classifier or detection capability.
- Extension behavior applies only to sites enabled by the user and content the browser exposes. Dynamic DOM text changes are now rescanned; hidden or inaccessible text, cross-origin frames/media, and protected/DRM pages may remain outside coverage.
- Controlled-page extension analysis/action/event persistence, the dashboard's post-pair refresh in the user's browser, offline/reconnection behavior, restart persistence and performance measurements remain outstanding. Extension loading, pairing and policy version 7 synchronization were confirmed by the user; no browser automation was performed for this status follow-up.
- Policy cache age defaults to 24 hours through `MORVIX_POLICY_CACHE_MAX_AGE_MINUTES`; this provisional value requires team/adviser confirmation. Stale cached rules are retained but not enforced offline; classification is unavailable while the backend is unreachable.
